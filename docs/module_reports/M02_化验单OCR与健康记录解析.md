## 二、流程走通性实测

**主链路**：上传 → OCR 抽取文本 → 指标解析 → 归一化 → 入库 → 供八轴打分消费

| 环节 | 状态 | 判据 |
|---|---|---|
| 引擎抽象层 | ✅ 通 | 4 个引擎实现 + `get_ocr_engine()` 工厂 |
| fail-loud | ✅ 通 | `OCRUnavailableError`，不可用时不静默伪造 |
| 指标解析 | ✅ 通 | `report_parser.py` 存在 |
| 入库 | ✅ 通 | `records.py` 端点存在 |
| **指标术语归一化** | ⚠️ **未见** | 未发现 LOINC / 中文别名词典层 |
| **参考区间与单位归一化** | ⚠️ **未见** | 不同医院单位（mg/dL vs mmol/L）、方法学差异未见处理 |
| **人工复核回路** | ❌ **未见** | 解析错了用户能否修改，未见明确入口 |

**关键判断**：OCR 层做得对（抽象 + fail-loud），**但真正决定"好不好"的三层——术语映射、参考区间、复核回路——全部缺失**。这三层恰好是研究指出的"唯一护城河"，也是当前空白。

## 三、是否符合人类使用习惯

| 维度 | 评价 | 说明 |
|---|---|---|
| 支持拍照上传 | ✅ 好 | 移动端刚需 |
| 上传后反馈 | ⚠️ 待确认 | 是否显示"正在解析 / 识别到 N 项 / 请核对" |
| **可修正** | ❌ **不合格** | OCR 对化验单的错识率客观存在（尤其拍摄畸变、多行表格）。**不允许用户修正的 OCR 是不可信的** |
| **可追溯** | ❌ **不合格** | 用户看不到"这个值是从单子哪一格来的"，无法建立信任 |
| 批量上传 | ⚠️ 待确认 | 用户往往有多年体检单，单张上传体验差 |

**最需要改的一条**：解析结果必须**逐项可编辑 + 高亮原文位置**。这不只是体验问题，更是**数据质量问题的唯一现实解法**——OCR 精度永远达不到 100%，复核回路把剩余误差交给用户（成本最低且用户有动机）。

## 四、市场与竞品对标

**需求判断**：真实但**供给严重过剩**。

| 竞品 | 定位 | 模式 | 短板 |
|---|---|---|---|
| ai-labtest.com | 化验单 AI 解读 | ~$1.90/份 | 单点工具，无留存 |
| LabbyQ / LabSense AI / BloodGPT | 同类 | 部分免费 | 同质化到按份收费 |
| Function Health | 100+ 生物标志物会员制 | 订阅（约 $365–499/年） | 自有实验室，重资产 |
| Superpower / InsideTracker / Lifeforce | 同类会员制 | 订阅 | 同质化 |
| **美年健康"血液学时钟"** | 2025-11 发布，国内首款 AI 衰老评估 | 体检流量变现 | 无干预闭环，无中医维度 |

**痛点已从"有没有"转向"好不好"**：解析精度、指标归一化、趋势追踪、合规输出。
→ **HealthLens 若只做 OCR 解读，毫无胜算；差异化只能来自"解析后接什么"（八轴 + 中医 + 合规）。**

## 五、可融合的开源技术

| 项目 | 许可 | 活跃度（检索所得） | 能解决什么 | 集成成本 | 建议 |
|---|---|---|---|---|---|
| **PaddleOCR** | Apache-2.0 | 91k★ / 2026-09 仍更新 | 中文 OCR 底座，拍照场景强 | 低 | **保留/强化**（已在用） |
| **docling** | MIT（LF AI & Data） | 68.8k★ / v2.138.0（2026-10） | 版面 + 表格 → 统一 IR，本地执行，MIT 商用最干净 | 低 | **首选引入**：表格是化验单的核心难点 |
| **MinerU** | Apache-2.0 变体（自研协议） | 81.7k★ / v4.0.12（2026-10-11） | 中文表格更强 | 低 | 可用，但**商用前过法务** |
| marker | Apache-2.0 | 40.4k★ / 2026-10 | PDF → Markdown 高精度 | 低 | 备选 |
| olmOCR | Apache-2.0 | 19.7k★，**最后提交 2026-03** | 批量 PDF | 中 | **不建议**（半停滞） |
| GOT-OCR2.0 | 无许可 | **最后提交 2025-02** | 端到端 OCR | 高 | **不建议**（已停滞） |

**取舍**：
- **直接用开源替换**：版面解析 / 表格抽取（docling 或 MinerU）。**一行都不要自研。**
- **必须自研（护城河）**：① 化验指标 → 标准术语映射（LOINC + 中文别名词典）；② 参考区间与单位归一化；③ 结构化结果的质量校验 + 人工复核回路。

## 六、提升方案

### P0（1–2 周）

| 项 | 动作 | 验收标准 |
|---|---|---|
| P0-1 | **解析结果可编辑**：每项指标允许用户修改，并保存"原始值 / 修正值 / 修正人 / 时间" | 任一指标可修正，修正留痕 |
| P0-2 | **原文位置高亮**：返回每个值的来源坐标/文本片段 | 前端可展示"这个值来自原文第 X 行" |
| P0-3 | 建指标别名词典（至少覆盖八轴消费的指标：glucose / hba1c / hs_crp / 血脂 / 血压 / BMI 等） | 同一指标的不同写法（空腹血糖 / GLU / FPG）归一 |

### P1（3–6 周）

| 项 | 动作 | 验收标准 |
|---|---|---|
| P1-1 | 引入 docling 处理版面与表格 | 多行表格化验单解析准确率有可测提升（建金标准集） |
| P1-2 | 单位与参考区间归一化层 | mg/dL ↔ mmol/L 自动换算；不同实验室参考区间分别存储 |
| P1-3 | 建**金标准测试集**（≥ 30 份真实化验单，脱敏） | 每次引擎变更跑回归，输出准确率/召回率 |

### P2（2–3 月）

| 项 | 动作 | 验收标准 |
|---|---|---|
| P2-1 | 批量上传 + 历史趋势自动对齐 | 多年体检单自动形成指标趋势曲线 |
| P2-2 | 异常值二次确认（与 M07 危急值联动） | 识别到危急值强制提示就医 |
