## 二、流程走通性实测

**主链路**：选择数据源 → 授权/上传 → `sync_data()` → 归一化 → 入库 → 供八轴消费

| 数据源 | 支持 `configure()` | 同步方式 | 状态 |
|---|---|---|---|
| `withings` | ✅ | OAuth2 | 通 |
| `huawei_health` | ✅ | OAuth2（需企业资质） | 通（**准入风险**） |
| `xiaomi_health` | ✅ | OAuth2（需企业资质） | 通（**准入风险**） |
| `hospital_lis` | ✅ | FHIR base URL + API key | 通 |
| `open_wearables` | — | 聚合层 | 通 |
| **`apple_health`** | ❌ | **用户手动导出 XML 再上传** | ⚠️ 非自动同步 |
| **`google_health`** | ❌ | **用户手动导出 JSON 再上传** | ❌ **且被后端拒绝** |

### 🔴 实测发现的确定性缺陷

**`app/api/connections.py:31`**：
```python
ALLOWED_SOURCE_TYPES = {"huawei_health", "apple_health", "withings",
                        "xiaomi_health", "hospital_lis", "open_wearables"}
```
**`google_health` 不在白名单内**，但：
- `frontend/src/components/WearableDevices.jsx:7` 明确渲染了 `google_health: '📱'`；
- `connectors.py:44` 的 `OW_PROVIDERS` 列表也含 `{"id": "google_health", ...}`。

→ **用户在前端点击"Google Health"，后端 `connections.py:76` 校验失败并返回 400。** 这是一条**用户界面可见但必失败**的死路。

## 三、是否符合人类使用习惯

| 维度 | 评价 | 说明 |
|---|---|---|
| OAuth 一键授权（Withings） | ✅ 好 | 符合习惯 |
| **Apple Health 需手动导出 XML** | ❌ **严重不符** | 用户要在 iPhone 健康 App 里导出、再回到网页上传。这是**技术限制**（HealthKit 无服务端 OAuth）但**体验代价极大**，多数用户会在这一步流失 |
| **Google Health 需手动导出 JSON** | ❌ **严重不符** | 同上，且当前**直接报错** |
| 华为 / 小米 | ⚠️ 不确定 | 需企业开发者资质 + 权限审核，周期不可控 |
| 失败反馈 | ⚠️ 待确认 | 授权失败是否给出可操作的下一步指引 |

**最需要改的一条**：Apple/Google 的"导出文件"路径**必须做成明确引导**（分步骤图文 + 说明为何需要这一步），否则用户只会认为是产品坏了。同时应把 `apple_health` / `google_health` 在 UI 上标注为"文件导入"，与 OAuth 类数据源区分开——**用户预期管理本身就是体验设计**。

## 四、市场与竞品对标

**需求判断**：真实且刚性强，但**瓶颈是准入不是技术**。

⚠️ **关键时间约束**：**Google Fit API（含 REST）支持至 2026 年底终止**，必须迁移到 Health Connect / Google Health API（云端）。当前 `google_health.py` 走的是本地 JSON 导出，虽然不受 API 终止影响，但也意味着**拿不到持续同步能力**。

| 竞品 / 参考 | 定位 | 开源 | 说明 |
|---|---|---|---|
| **Open Wearables** | 统一 Apple/Whoop/Oura/Samsung 等聚合层 | **MIT** | 含 Sleep/Resilience 开放评分算法 + MCP；**v0.9.0（2026-09），未到 1.0** |
| Terra | 商业可穿戴聚合 API | 否 | 覆盖广，按调用计费 |
| Medplum | FHIR 服务器 + 合规托管 | Apache-2.0 | 完整但需换栈（TypeScript） |
| openmhealth/schemas | OMH 数据模式 | Apache-2.0 | **社区实质沉寂，不建议押注** |

## 五、可融合的开源技术

| 项目 | 许可 | 活跃度 | 能解决什么 | 集成成本 | 建议 |
|---|---|---|---|---|---|
| **Open Wearables** | MIT | 2.65k★ / v0.9.0（2026-09-17） | 国际侧连接器骨架，FastAPI 原生，评分算法开源可审计 | 低（但**未含华为/小米/Health Connect**，需自补） | **建议引入作骨架** |
| **fhir-py** | MIT | 218★ / 2026-10 | 轻量 FHIR 客户端 | 低 | 替换自建 FHIR 交互 |
| fhirclient (SMART on FHIR) | — | 696★ / 2026-09 | OAuth 授权流程 | 低 | 医院 LIS 侧可用 |
| Medplum | Apache-2.0 | 2.74k★ | 完整 FHIR 服务器 | 高 | 暂不建议（换栈成本） |

**取舍**：
- **直接用开源**：国际连接器骨架（Open Wearables）、FHIR 客户端（fhir-py）。
- **必须自研**：华为 / 小米 / 医院 LIS 适配器（开源无覆盖，且**审批资质本身是壁垒**）；统一指标语义层 + 去重与冲突消解；合规审计日志。

## 六、提升方案

### P0（1 周内，必须）

| 项 | 动作 | 验收标准 |
|---|---|---|
| P0-1 | **修 `ALLOWED_SOURCE_TYPES`**：加入 `google_health` | 前端点击 Google Health 不再 400 |
| P0-2 | **加一致性测试**：`OW_PROVIDERS` / 前端设备列表 / `ALLOWED_SOURCE_TYPES` 三处必须是同一集合 | 三处不一致 → CI 红 |
| P0-3 | Apple/Google 在 UI 上标注"文件导入"，并提供分步骤引导 | 用户能独立完成导出上传 |

### P1（3–6 周）

| 项 | 动作 | 验收标准 |
|---|---|---|
| P1-1 | 评估引入 Open Wearables 作为国际侧骨架 | 至少覆盖 Oura/Garmin/Fitbit 三家可用 |
| P1-2 | 补 Health Connect 适配器（Google Fit API 2026 底终止） | 有明确迁移路径与排期 |
| P1-3 | 统一指标语义层：LOINC 归一 + 多源冲突消解（如体重来自三个源） | 同一时刻同一指标有唯一取值与来源标注 |
| P1-4 | 同步状态可视化：上次同步时间 / 成功条数 / 失败原因 | 用户可见可操作 |

### P2（2–4 月）

| 项 | 动作 | 验收标准 |
|---|---|---|
| P2-1 | 增量同步与断点续传 | 大数据量不超时 |
| P2-2 | 数据质量评分（缺失率、异常值）反馈给用户 | 用户知道数据是否够用 |
